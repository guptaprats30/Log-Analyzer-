# Log Anomaly Detection

A Python tool that parses raw server logs, aggregates events into time-series buckets, and flags anomalous time windows using two independent approaches: a rolling z-score baseline and an unsupervised ML model (Isolation Forest).

## Motivation

Production systems generate far more log output than anyone can read. The useful signal — "something broke around 11:40" — is buried in thousands of routine lines. Fixed rules like `if errors > 10: alert()` don't generalize: a busy service might normally produce 50 errors a minute, while a quiet one producing 3 is already in trouble.

This project takes the alternative approach: learn what "normal" looks like from the data itself, then flag deviations from it.

## How it works

**1. Parsing.** Reads a raw log file line by line, extracting timestamp and log level. Malformed lines (bad dates, invalid levels, truncated entries) are filtered out rather than crashing the pipeline.

**2. Feature engineering.** Events are bucketed into fixed time intervals (default 5 minutes) using pandas `resample`. Each bucket becomes a feature vector: per-level counts (`ERROR`, `WARNING`, `CRITICAL`, ...) plus total log volume.

**3. Detection.** Two methods run over the resulting time series:

| Method | How it works | Catches |
|---|---|---|
| Rolling z-score (`window=10`) | Compares each bucket to the mean/std of the 10 preceding buckets, per column | Sudden deviations from recent local behavior; interpretable and time-aware |
| Isolation Forest (`contamination=0.1`) | Treats each bucket as a point in feature space; anomalies are easier to isolate via random splits | Unusual *combinations* of features, regardless of time ordering |

Running both is deliberate — they make different assumptions and catch different things.

## Results

Validated against a synthetic log (4 hours, ~550 lines, generated by `generate_synthetic_log.py`) with three deliberately injected anomaly windows:

- **09:00–09:05** — burst of ERROR/CRITICAL logs
- **10:30–10:33** — near-total logging silence (simulated crash)
- **11:40–11:46** — larger error burst

**Isolation Forest** flagged all three windows correctly:

| Bucket | Window | Result |
|---|---|---|
| 09:00 | error spike | Caught |
| 10:30 | outage | Caught |
| 11:40, 11:45 | error spike | Caught |

Notably, the outage window was flagged despite containing *zero* errors — Isolation Forest caught the collapse in total log volume, which a naive error-count threshold would have missed entirely.

**Rolling z-score** correctly flagged the 10:30 outage and the 11:40–11:45 spike, but missed the 09:00 spike. This is a known limitation, not a bug: with `window=10`, the first 10 buckets don't have a full window of prior history to establish a baseline — early in the log, the rolling window is still partly built from the anomalous data itself, which dampens the z-score. A larger warm-up period before evaluating, or seeding the window with known-normal data, would resolve this.

## Usage

```bash
pip install -r requirements.txt

# Generate test data with known anomalies
python generate_synthetic_log.py

# Analyze a log file
python analyze.py synthetic_log.txt --search disk
```

## Expected log format

```
YYYY-MM-DD HH:MM:SS LEVEL message text here
2026-08-16 09:03:12 ERROR Database connection failed
```

Recognized levels: `INFO`, `DEBUG`, `WARNING`, `ERROR`, `FATAL`, `CRITICAL`.

## Files

| File | Purpose |
|---|---|
| `analyze.py` | Main pipeline: parsing, bucketing, detection, reporting |
| `generate_synthetic_log.py` | Generates test logs with injected anomalies |
| `synthetic_log_ground_truth.txt` | Which windows were deliberately made anomalous |
| `summary.txt` | Output: counts, percentages, keyword matches |
| `log_level_distribution.png` | Bar chart of log level counts |

## Tools

Python, pandas, NumPy, scikit-learn, matplotlib

## Possible extensions

- Fix the z-score cold-start issue (warm-up period or seeded baseline)
- Stream mode (`tail -f`-style) for live monitoring instead of batch analysis
- Configurable log format via regex, to support nginx/syslog/JSON logs
- Alerting hook (webhook/email) when anomaly rate crosses a threshold
- Persist results to a database with a queryable dashboard
